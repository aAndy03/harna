# Boundaries as capabilities: owns/escapes, banned-api into clippy, cargo-layering, sync groups; pressure counts only undeclared crossings (0.3.45)

From the deno study. Ownership is a container declaration (owns/escapes) like gateway: capability types are guarded at construction only (holding is fine — the type-system pattern deno uses), markers anywhere outside the owner; escape hatches are counted errors so baselines ratchet them (rejected: allow-listing escape sites in data — a count with a direction is simpler and already supported). banned-api is rule data (values) and harna deny writes it into clippy.toml for crates a rule fully covers (rejected: narrower scopes writing crate-wide bans). A reasoned file-level allow(clippy::disallowed_methods) exempts the implementing file, mirroring clippy. cargo-layering reads Cargo deps through the same CrateIndex::cargo_deps adopt drafts from, so a fresh draft passes it. sync-group uses the rule's pattern as its extractor (takes_pattern), not as a naming rule. Pressure: declared depends_on reaches are the architecture, not pressure. Facade edges (parent -> own descendant) are structure, not cycles; a name public anywhere in a container shadows a private namesake. Also: harna's installed binary was 0.3.41 while the repo was at 0.3.44 — the hooks judged with stale rules; reinstall is now part of the release ritual.
