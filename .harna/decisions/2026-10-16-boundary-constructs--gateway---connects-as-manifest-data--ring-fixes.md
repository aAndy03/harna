# Boundary constructs: gateway + connects as manifest data; ring fixes

Decision 2026-10-16, shipping in 0.3.10: boundary constructs arrive as manifest data. A container declares its facilities with a gateway field (fs | fs:write | net | process | base, comma list; the :write qualifier narrows fs enforcement to the write side) and its corridors with a connects field (two or more layer names). Declaring is the adopting; no declaration, no gate. harna dogfoods the fs/process half by owning its storage writes (schema, generation, conformance containers) and its git subprocess calls (search, conformance, composition, cli containers); the transit half ships without adoption because harna has no corridor by design - its cross-layer imports ARE the layered architecture it verifies. The gateway field deliberately was NOT modeled as role = values or another enum pivot: role classifies who a container is, gateway admits what a container touches; one field per concern. This is container metadata next to role/provides, not a rule about code paths. Registry constructs are NOT faked as a check; that boundary is documented honestly in the changelog. The dogfood run also surfaced REAL module-graph rings the old copy-pasted resolver had silently bypassed: its tie-break compared the host stem length against the best-so-far PATH length, so the first filesystem-ordered host always won and ring edges landed on a dead end. Fixing host resolution in 0.3.10 (hosted_module) surfaced all of them; Severity+Violation moved to enforcement/violation.rs and decisions::list now takes a directory - both rings broken for real, not papered over by making the checker blind.
