# Adopt drafts the manifest proposal; the tree speaks first, the tool only proposes

Decision 2026-10-17, shipping in 0.3.20: harna adopt (CLI) + harna_adapt (MCP tool 25) draft a manifest from the existing folder tree - the Phase E collaboration opener. THE PROPOSAL IS DATA: one layer per crate dir straight off the map (crate_of over the pure build_incremental scan - no .harna write, a draft is a proposal about an unadopted repo), layer names from each crate's own Cargo.toml package name (root crate folded first via Option's None<Some order), cross-crate import direction proposed as depends_on via metrics::resolved_edges (the one shared resolution - 0.3.19 doctrine kept), one container per crate src, one primitive component per module with its line count in a draft:-marked summary (a marker to replace with prose). STDOUT ONLY: summary line to stderr, manifest TOML to stdout - redirecting yields paste-ready TOML; adopt never writes the manifest (the adopter prunes, renames, then commits it); refuses non-empty manifests (a malformed manifest still errors - the missing-file case IS the fresh start). SCOPE EXCLUSIONS said plainly: no intra-crate container grouping (intent, not structure - no evidence to invent it; per-module sizes give the adopter the material), no gateways/provides/budgets drafted (empty stays ungated by design), no new lines field in the digest (sizes are a one-time second read - the map's data format stays untouched, protocol stable). EDGE CASES pinned by 3 tests: deterministic layer order, unique component names (leaf/full-stem/numbered), loader-honest TOML round-trip. 205/205 tests, validate 0 error (8 info tolerated), doctor 11 ok, parity harna-0-3-20 4/4 ack+resolved, dogfood refusal verified on harna itself + real draft verified on a pristine temp copy (54 modules, 3 object layers, depends_on cli->core).
