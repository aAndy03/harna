## 1. `adopt --by-dir`

```
$ harna adopt --by-dir > draft.toml
draft: 6281 module(s) across 7 layer(s)/104 container(s); 2118 cross-crate edge(s) proposed as depends_on
calibrated budgets ...: component-granularity limit 2200, folder-size limit 24
```

Layers produced: `cli` (5 crates), `ext` (30), `libs` (29), `runtime` (4), `tests` (34), `tools` (1), `root` (1). The first-level grouping matches deno's real top-level folders (cli/, ext/, runtime/, libs/, tests/, tools/), which is what `--by-dir` promises. Good.

### Bug A: every JS/TS file lands in a synthetic `root` layer, not in its folder's layer

- Layer `root` / container `adopted` (path `.`) holds **5,266 components, 31,000 of the 38,000 draft lines**. 5,225 of them are JS/TS (`ext/node/polyfills/*.ts`, `ext/web/*.js`, `cli/tsc/*.ts`, `runtime/js/*.js`, `tests/specs/**`, `.github/workflows/*.ts`, `tools/*.js`).
- So `ext/web/06_streams.js` is in layer `root`, container `adopted`, while `ext/web/blob.rs` is in layer `ext`, container `deno_web`. The by-dir grouping only applies to Rust; JS is not bound to the folder/crate it sits in.
- Consequences: layer-boundary / cargo-layering checks never see JS in `ext`; `root` carries `depends_on = ["tests"]` for no reason; the draft says "1 crate(s) as containers" for 5,266 modules.
- `harna dependents cli/tsc/97_ts_host.js` still says "hosted by: layer cli, container deno" (path-prefix lookup), but the manifest has it in `root`. Two places answer "who hosts this file" differently.
- Also some Rust-adjacent fixtures (`ext/cache/01_cache.js`, in an existing crate dir) sit in `root` too, so it is not only "no crate here".
- Fix: attach a JS/TS file to the nearest enclosing container path (crate dir), else to the top-level folder layer. Never to `.`.

### Draft noise (needs pruning by the adopter)

- 4,287 of the draft's JS components are under `tests/` (3,083 `tests/specs`, 489 `tests/testdata`, 435 `tests/registry`, plus unit/bench/napi). `tests/specs/**` generated 34+ "containers" named like fixtures (`1_0_0`, `pkg_a`, `pkg_b`, `main_project`, `folder_ts_file`, `multiple_entries` ...) because each fixture has a Cargo.toml/package.json. These are not architecture.
- `.github/workflows/*.ts` (12) are components.
- Suggest: `adopt` should skip dirs named `testdata`, `fixtures`, `specs`, `node_modules` and cap/aggregate (one component per folder when a folder holds > N tiny files), or print a "pruning hints" list. A `--exclude <glob>` option would help (none exists).
- Every component is `kind = "primitive"`, `summary = "draft: N lines"`, names are file stems; collisions are disambiguated ad hoc (`06_streams_js`, `cargo_publish_ts`). Names like `check`, `node`, `args` in `cli/cache/*` are ambiguous.
- Stderr gives helpful "calibrated budgets" commands, but those two `harna add-rule` lines are on stderr, the TOML on stdout - fine for redirect, but easy to lose. OK.

### Are the `depends_on` edges plausible?

```
cli     -> ext, libs, runtime
ext     -> libs, root, runtime, tests
libs    -> cli, ext, runtime, tests
runtime -> ext, libs
root    -> tests
tests   -> cli, libs, root
```

- They are mechanically true (imports exist) but not a layering: the layers form one strongly connected component. `validate` says so: `[?manifest-depends] depends_on cycle: cli, ext, libs, root, runtime, tests cannot be ranked (strict layering checks skip these layers until the cycle breaks)`.
- Real reasons: deno's `runtime/` holds the base crates `deno_permissions`, `deno_features`, `deno_subprocess_windows`, which every `ext/*` crate uses, while `runtime/` itself uses `ext/*`. `libs/cli_parser` depends on `deno_runtime`. So top-level folder != layer in deno; `--by-dir` cannot give a DAG here, and that is a legitimate finding about deno, not a harna bug.
- `libs -> tests` and `ext -> tests` are test-only (dev-deps / test helper crates `test_util`). `ext -> root` / `root -> tests` are artifacts of Bug A.
- When I replaced depends_on by a "natural" DAG (cli > runtime > ext > libs, tests > all), validate produced **145 `layer-boundary` + 25 `cargo-layering` errors**, nearly all `ext/* -> deno_permissions / deno_features (runtime)`. Correct detection, but it shows the DAG a human would guess is wrong; the real fix is moving `runtime/permissions`, `runtime/features` into a lower layer (container `path` override). Suggest: when the SCC cannot be ranked, `adopt` should print the one-line hint "N layers form a cycle; the smallest pieces causing it are: runtime/permissions, runtime/features" (the containers imported by the most other layers while importing back).
- Suggest `adopt --by-dir` order layers by SCC condensation and emit a comment naming the cycle edges, instead of silently writing a cyclic `depends_on`.

### The big miss: deno's own JS module graph is invisible

Nearly every `ext/` file answers "nothing imports it":

```
$ harna dependents ext/web/06_streams.js   -> nothing imports ... directly
$ harna dependents ext/node/polyfills/fs.ts, ext/fetch/26_fetch.js, runtime/js/99_main.js, ext/web/02_event.js -> same
```

Cause (in this deno revision): ext JS is wrapped in IIFEs and uses `core.loadExtScript("ext:deno_node/_fs/_fs_common.ts")` (914 occurrences under ext/runtime/cli), plus 161 single-line `import ... from "ext:..."` and `from "node:..."` (66). The `ext:<crate>/<path>` scheme is deno-specific (resolution via the Rust `extension!` macro's `esm = [...]` list).

Misclassifications / false negatives:
1. `ext:` specifiers are reported as **npm packages**: `npm:ext:core` (123), `npm:ext:deno_node` (32), `npm:ext:runtime` (5), `npm:ext:cli` ... Worse, `package_of()` truncates `ext:deno_node/internal/buffer.mjs` to `npm:ext:deno_node`, throwing away the file part, so even a resolver could not recover the target from the digest.
2. `node:fs` -> `npm:node:fs` (57 distinct node: builtins reported as npm packages). A `builtin:`/`node:` kind would be cleaner and would keep them out of "npm dependency" listings.
3. `core.loadExtScript("...")` string calls are not edges at all. This is the actual JS-to-JS dependency of deno. A generic, data-declared "JS call pattern -> specifier" would cover it (see suggestions).
4. Rust -> JS wiring (`deno_core::extension!(deno_web, esm = ["00_infra.js", ...])` in `lib.rs`) is not an edge either, so `ext/web/lib.rs` does not show `ext/web/*.js` as a relationship and a JS file looks orphaned. `harna tree`/"unreachable-module" does not flag JS (fine), but `dependents` is blank.

`file?:` misses (252): 188 `tests/specs`, 23 `tests/testdata`, 21 `tests/registry`, 7 `tests/unit`, 5 `libs/eszip`, 3 `tests/bench`. Non-test: 

```
ext/node/update_node_stream.ts           file?:../../tests/node_compat/runner/suite/node_version.ts   (genuinely absent: not checked out)
libs/eszip/testdata/emit/main.ts          file?:./a.ts   (fixtures; real misses are intentional test data)
libs/eszip/testdata/source/mapped.js      file?:a        (import-map bare spec)
.github/workflows/npm_publish.ts          file?:./$DIST_DIR/deno/package.json   (template string)
tools/update_import_map_for_tests.ts      file?:../tests/util/std/deno.json  (JSON import, file absent)
```

So `file?:` is accurate: no wrong resolutions found among the 1,185 `file:` edges spot-checked (cli/tsc chain). The `file?:` list is just a dozen real non-test items - good signal. But `validate` has no check to list unresolved JS imports; they are only visible in the digest JSON (`grep 'file?:' .harna/digest/shards`). Suggest `harna deps --unresolved`.

Noise: bare npm imports from fixtures: `npm:npm:@denotest` (144), `npm:jsr:@denotest` (45): the `npm:`/`jsr:` scheme gets double-prefixed (`npm:npm:@denotest`, `npm:jsr:@denotest`). Cosmetic but ugly.

Multi-line imports: not examined in depth; the `^import ... from` stats I did were single-line. `ext/net/03_quic.js`, `ext/image/01_image.js` etc. have static `import { ... } from "ext:core/mod.js"`, resolved as `npm:ext:core`.

## 3. Rust <-> JS boundary: the `deno-ops` plugin

### What deno's real patterns are (measured over ext/runtime/cli/libs/tools JS, 601 files)

| pattern | occurrences |
|---|---|
| `core.ops.op_x(` | **11** matches (3 files) |
| bare `ops.op_x(` | 40 (5 files; 8 are not ops, e.g. `ops.write`) |
| `const { op_a, op_b } = core.ops;` destructuring | **117 blocks, 115 files, 812 distinct names** |
| `import { op_a, ... } from "ext:core/ops"` | **36 blocks / files, 222 names** |
| any `\bop_*` mention | 2,503 across 161 files, 1,002 distinct ops |

So the pattern the task brief names first (`core.ops.op_x(`) is the *rare* one. 98% of references are destructured or imported, and many destructure blocks are multi-line with trailing comments. Rust side: 1,451 `#[op2` markers, 1,275 distinct fn names; 23 markers have no `fn` within 6 lines (long attribute lists, e.g. `ext/crypto/crypto.rs:7`, `ext/net/lib.rs:225`, `ext/node/ops/perf_hooks.rs:36`).

### Bridge attempts (plugin `deno-ops`, installed with `harna plugin add <path>`)

Install output: `plugin deno-ops 0.1-1 added (../deno-plugin): 0 rule(s), 0 term(s)` / `mirrors deno_core 0.0.0`. (A plugin with no rules and a made-up `[mirrors]` entry is required by `plugin.toml`? `mirrors` is optional I believe, but I declared one, and `doctor` then warned `deno-ops mirrors deno_core 0.0.0, Cargo.lock has 0.412.0` - correct and useful, but see S9.)

1. **Strict** (`rust = '#\[op2'`, `ts = '\bops\.NAME\b'`): scan -> **21 edges / 17 JS files / 11 Rust targets**. Precise but recall ~1% (matches only `core.ops.x` and `ops.x`).
2. **Loose with the op2 marker** (`rust = '#\[op2'`, `ts = '\bNAME\b'`): **3,661 edges / 1,829 JS files / 114 targets**. Garbage: `#[op2]` also marks cppgc methods named `new`, `constructor`, `width`, `id`, `create`, `message`, `resolve`. Every JS file containing the word `new` or `constructor` links to the first Rust file defining one: `ext/node/ops/handle_wrap.rs` gets 1,525 "callers", `runtime/ops/desktop.rs` 491, `ext/webgpu/shader.rs` 401. Unusable.
3. **Name-anchored** (final): marker on the fn line itself, `rust = '\bfn\s+op_[A-Za-z0-9_]*'`, `ts = '\bNAME\b'` -> **283 edges / 185 JS files (163 outside tests/) / 110 Rust targets**, no `new`/`constructor` pollution. Of the 167 non-test JS files that mention `op_*`, 163 got a bridge edge; the 4 misses are stale (`libs/core/examples/wasm.js` refers to `op_get_wasm_module`, not defined in Rust; `_brotli.js` uses `op_brotli_*` with no Rust definition - not a harna miss).

```
$ harna dependents ext/os/lib.rs
dependents of `ext/os/lib.rs`: 21 direct, 0 knock-on (ring 2)
  ↳ cli/js/40_test.js (via bridge:ext/os/lib.rs)
  ↳ ext/node/polyfills/01_require.js (via bridge:ext/os/lib.rs)
  ↳ ext/os/30_os.js ... runtime/js/90_deno_ns.js ... runtime/js/99_main.js ...
$ harna dependents ext/web/timers.rs
  ↳ ext/web/02_timers.js (via bridge:ext/web/timers.rs)
  ↳ ext/web/15_performance.js (via bridge:ext/web/timers.rs)
  ↳ ext/web/lib.rs (via crate::timers::StartTime)
$ harna whereis op_fs_open_sync
  - ext/fs/ops.rs — pub fn op_fs_open_sync( (`fn`, pub)
referenced by 6 module(s): ext/fs/30_fs.js, ext/fs/lib.rs, ext/node/polyfills/01_require.js, ...
```

This works well and `whereis` is a nice cross-language lookup. Limits of the regex-bridge model discovered:

- **One match = one NAME.** `captures_iter` yields non-overlapping matches, so a regex anchored on the destructure context (`\{[^{}]*NAME[^{}]*\}\s*=\s*core\.ops`) links at most one op per block. Lookahead isn't available (Rust regex). So destructuring cannot be matched precisely; the only workable regex is "any mention of the identifier". That means mentions in comments/strings count (the TS side strips comments for imports, but bridges read raw source), and a name that appears in a JS file for another reason links. In deno `op_*` is a unique-enough prefix, but the bridge can't say "NAME must start with op_".
- **The bridge cannot constrain NAME**; the Rust marker has to carry that (my trick: put the name filter in the `rust` regex, matching the `fn` line). That works only because harna matches the marker per line and then searches for `fn <name>` starting at the marker line. This behaviour is undocumented; worth documenting as the idiom (or add a `name = "^op_"` filter field).
- **First wins on duplicate names**: `op_print` is defined in 4 files (ext/io/lib.rs, cli/ops/jupyter.rs, cli/ops/lint.rs, libs/core/ops_builtin.rs) and `op_is_cancelled`, `op_is_node_file`, `op_blob_read_part` in 2; the edge goes to whichever file the scan visited first (non-deterministic across layouts; should link to all, or prefer the same container/crate).
- **6-line window**: `#[op2]` attributes with long argument lists push the `fn` out of the window; 23 of 1,451 markers (1.6%) missed in the strict form. The `fn op_` form avoids this.
- **Bridge edges are per (JS file, Rust file) pair**; no op-level detail ("which op") in `dependents` output, only "(via bridge:ext/os/lib.rs)". Showing the op names ("via op_exit, op_set_exit_code") would make the edge actionable.
- **Tests are included**: 22 of the 283 edges come from `tests/**` JS - fixture noise unless excluded. The bridge has no path scope.
- **No feedback at scan time**: `scan` prints no bridge count ("N bridge edges linked"); `link_bridges` returns the number but it isn't shown. I had to count `bridge:` entries in the digest JSON. `harna plugin show deno-ops` should list the bridge and `status` / `doctor` should say "bridge deno-op: 283 edges, 110 targets, 0 unmatched names".
- **No check that a bridge matched anything**: a regex typo yields 0 edges silently (doctor said all fine). Suggest doctor `warn  bridge deno-op links 0 edges`.
- Not covered by any single bridge: `ext:core/ops` imports under an alias (`import { op_x as y }`), `Deno.core.ops` dynamic access `ops[name]`, and the Rust-side `#[op2]` fns defined by macro expansion. The non-`op_` named ops (20 names such as `verify_ed25519_b64`, `new_pipe`): didn't find any JS references under those names, so no loss observed.

Verdict: a regex bridge fits the *concept* but only reaches deno's real patterns via the "any mention" loose form + the name filter in the Rust marker. Strict `core.ops.op_x(` form recovers ~1% of the real references.

## Bug / false-positive / confusing-message list

1. **[bug, high]** `adopt --by-dir`: JS/TS files are assigned to layer `root` / container `adopted` (path `.`) instead of their top-level-folder layer. 5,266 of 6,281 components. Defeats by-dir for JS and the new TS map.
2. **[bug, high]** `ext:` specifiers recorded as `npm:ext:<crate>` with the path dropped (`npm:ext:deno_node`); `node:` as `npm:node:*`; `npm:`/`jsr:` double-prefixed (`npm:npm:@denotest`). No resolution of `ext:<crate>/<path>`.
3. **[gap, high]** `core.loadExtScript("ext:...")` (914 uses) and Rust `extension!(esm = [...])` produce no edges; `dependents ext/web/06_streams.js` is blank for nearly every ext file.
4. **[bridge model]** One NAME per regex match; no lookahead -> destructuring can't be matched structurally; need "any mention" + name filtering in the Rust marker. Duplicate names go to first file only. 6-line window misses 1.6% of `#[op2]`.
5. **[confusing]** `scan` always reports "scanned 74" files even when nothing changed (reused 6275) - which 74? (bridge-relinked / always-dirty files?) and no bridge count is printed.
6. **[noise]** `[!no-cycles]` error by default on Rust module cycles; `rules-coverage` prints one line per container (104).
7. **[noise]** adopt writes fixtures (`tests/specs/**`) as containers/components; no `--exclude`.
8. **[inconsistency]** `dependents` "hosted by" reads path prefix; manifest says `root`. After fixing Bug 1 these will agree.
9. **[perf]** `dependents`/`whereis`/`metrics`: 1.2 s each because the full 11 MB digest is parsed per call; `validate` 16 s.
10. **[doc]** `plugin.toml` bridge semantics (marker matched per line; `fn` searched from marker line for 6 lines; regex on raw source incl. comments; first-wins) are only in source. A plugin author needs them.

## Suggestions

S1. Bind JS/TS to the nearest container or the by-dir layer; never `.`. Add a test: a repo with `ext/a/Cargo.toml + ext/a/x.js`.
S2. Teach the TS reader a `ext:`/`node:` scheme: classify `node:`/`ext:` as `builtin:` (not npm), keep the path, and let a plugin map `ext:<name>/` -> folder (`deno_web` -> `ext/web`, derived from the container whose Cargo package is named `deno_web`; harna already knows crate names per container, so `ext:deno_web/02_event.js` -> container `deno_web` path + `02_event.js` is mechanical).
S3. Add a `[[js_calls]]`/`[[imports]]` plugin entry: a regex with SPEC capture treated like an import specifier (covers `core.loadExtScript("...")`, `require_ext("...")`, webpack `import()` wrappers).
S4. Add `[[bridges]]` options: `name_filter = "^op_"`, `scope = ["ext", "runtime", "cli"]` / `exclude = ["tests/**"]`, `multi = true` (all names in a match range; destructuring), `strip_comments = true`, and link to *all* definitions of a duplicate name (or prefer same-container).
S5. Print `bridge deno-op: N edges (M js files -> K rust files)` at scan end; `plugin show` and `doctor` flag a bridge with 0 edges; `dependents` should append the matched names ("via op_exit, op_set_exit_code").
S6. Provide a Rust->JS bridge for `deno_core::extension!(esm = [...], esm_entry_point = ...)` (a bridge kind in the opposite direction, or an `[[extension_files]]` regex): marker lines `esm = [`, list of string literals, resolved relative to the crate dir.
S7. `adopt`: `--exclude <glob>` (default skip `testdata`, `fixtures`, `node_modules`, `specs`), cap the JS/TS component list or group per folder when a folder holds > 50 files; mark `tests/` as `role = test`. Print the SCC note when `--by-dir` layers form a cycle and propose moving the smallest container(s) to break it (`runtime/permissions`, `runtime/features` in deno).
S8. `no-cycles`: default advisory when no rule binds it (like all other checks), or only error across containers; `rules-coverage`: collapse to a count + the first 5.
S9. Document in `plugin --help`/`plugin show` which fields are optional; `[mirrors]` with a fake version produced a doctor warn. Offer `harna plugin new <name>` to scaffold a plugin.toml with a `[[bridges]]` example (I had to read the harna source to learn the schema and the 6-line window).
S10. Cache or mmap the digest for `dependents`/`whereis` (1.2 s per query on an 11 MB digest). Consider a binary index next to the JSON shards.
S11. `harna manifest drop --path <glob>` / `harna component rm`, so pruning an adopted draft needs no scripting; and an `adopt --apply` that writes `.harna/manifest.toml` directly with a pruned default, since every adopter does init -> paste.
S12. An unresolved-import report: `harna deps --unresolved` listing `file?:` entries grouped by folder (252 here; only a dozen are outside tests).
