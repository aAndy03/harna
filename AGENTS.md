# Agent instructions

This repository is harna — it manages itself with harna.

- **Source of truth is `.harna/`** (manifest.toml, rules.toml, decisions/, digest.json).
  Start every session by calling the `harna_onboarding` MCP tool.
- **After an edit burst**, call `harna_validate` with `changed_only: true`
  (or run `harna validate --changed`). Fix violations before committing.
- **Structure changes**: update `.harna/manifest.toml` in the same commit as the code,
  and call `harna_log_decision` for any non-obvious choice.
- **After a structural change burst**: `harna parity open <id>` to turn the diff into
  parity targets, then `harna_parity` (action resolve) for each (ack or noop). Open debts
  gate validation.
- **New rules**: when the user states a preference or a convention is agreed, persist it
  immediately with `harna_add_rule` — instructions become data, not chat.
- **Before compaction / running out of context**: record the burst with
  `harna handoff` (summary + declared next steps) — `harna_onboarding`
  carries it into the next session; `harna status` reminds while it is open.
- **Containers never import each other sideways** in harna-core; composition may reach down.
  Layer map: `crates/harna-core/src/{schema,search,enforcement,generation,composition}`.
- Commit `.harna/` together with the code change it describes (atomic PRs).

## Born modular (0.3.26, rule `born-modular`, check `born-size`)

Per-scope files from the first line: scaffold the components first, then fill
them. Never write one oversized file intending to split it later — a new file
born over its budget (`limit = 600`) is an ERROR at `validate`, while files
with history stay covered by the advisory `component-granularity`/`hotspot`
checks. The vocabulary mapping sits in `.harna/terms.toml` (glossary:
agent vocabulary -> harna vocabulary; carried in every onboarding, audited
by `harna doctor`, exposed as the `harna://terms.toml` MCP resource).
Decline and failure are data too: `.harna/non-goals.toml` (deliberate
refusals — plan suppresses fully-covering proposals) and
`.harna/lessons.toml` (tried-and-failed with verdicts and evidence —
place/plan surface them as prior attempts); audited by `harna doctor`,
exposed as MCP resources, `harna non-goal add` / `harna lesson add`.
The path forward is data too: `.harna/roadmap.toml` (declared milestones:
declared|current|done|dropped — status/onboarding surface the NOW,
validate keeps it coherent, deferred reviews can key to a milestone id;
shipped means `harna roadmap set <id> done`).

Autonomous ritual (trusted agent, auto-mode — each step is an audit point):
plan -> scaffold -> implement -> `harna finish` (refreshes map and views,
checks the change, lists what is left) -> parity open -> resolve (real acks +
noops) -> suite -> preflight -> handoff -> atomic commit.

### Rules

- `no-hardcoded-urls`: No http(s):// literals outside endpoint/constants modules — why: URLs must be swappable per environment; hardcoded ones broke staging deploys in past projects (scope: crates)
- `born-modular`: Code modularly from the start: every file is written per-scope and within its container's component budget at birth; never write an oversized file intending to split it later — why: Retro-splitting wastes agent context and review time. Structure is born correct (harna's own generation-layer principle): 0.3.26 adds the born-size check so a new file over the bound rule's limit is a validation error, not a leftover debt; existing files stay covered by the advisory hotspot/component-granularity checks (scope: crates; check: born-size)
- `folder-budget`: A folder holds at most 8 source files; group related files into sub-folders — why: Flat folders made agents encode grouping in file names (8 *_data.rs files in schema/); the tree is the structure (0.3.39) (scope: crates; check: folder-size)
- `no-name-clusters`: Files sharing a name token (3+) live in a folder named after it, not side by side — why: *_data.rs, cmd_*.rs, hook_*.rs are folders that were never created; harna move makes the fix one command (scope: crates; check: name-cluster)
- `flow-and-maintenance`: Every release also optimizes harna's own usage flow (fewer steps, fewer calls, clearer output) and keeps everything maintained: each change goes through parity, and features that ship stay coherent with the rest — why: The user's standing principle (2026-10-19): harna is used daily by agents, so friction compounds across versions; parity exists so nothing silently rots as features accumulate
- `suppression-reason`: Every #[allow] says why (reason = "…") — why: An exemption without a reason cannot be reviewed; deno study B2 — adopted on harna itself (check: suppression-reason)
- `tools-not-prescriptions`: harna ships tools (checks, profiles, plugins, catalogs) as data the agent or engineer chooses to use; it never hardcodes a product decision (auth, licensing, offline vs online, a framework's API) into harna's code — why: The user's standing principle (2026-10-20): harna is like Figma — it shows tools, it does not dictate the design. Domain and framework knowledge (gpui-kit 0.8.0, TypeScript) lives in versioned data packs/plugins that track their upstream API, so harna's core stays general
- `engines-import-declared-layers`: Each layer imports only itself and the layers it declares in depends_on; a hand-off several layers share goes through one declared corridor (transiter) instead of direct edges — why: Direct coupling made the billing engine unreusable in earlier projects; depends_on is what harna enforces today, corridors are the tool for a shared hand-off when one appears (scope: crates; check: layer-boundary)
- `practices/errors-are-not-swallowed`: An error is handled or passed on, never caught and dropped: no empty catch block, no Err(_) arm that does nothing — why: Agents silence errors to make a run pass; the failure then surfaces far from its cause, or never. Handle it, return it, or log it with context (check: code-pattern)
- `practices/no-silent-fallbacks`: A failure is not turned into a plausible default: no catch that returns an empty value, no Err(_) arm that returns one — why: A silent default (an empty list, null, 0) looks like real data; the screen shows nothing and nobody knows why. Fail visibly or make the fallback a decision (check: code-pattern)
- `practices/no-placeholders`: No placeholder left in shipped code: TODO, FIXME, XXX, HACK, todo!() or unimplemented!() — why: Agents leave stubs that compile; a placeholder in shipped code is a feature that silently does not exist. Record the gap as a deferral or a roadmap item instead (harna deferred add). With many today, freeze the count: harna baseline record --check code-pattern (check: code-pattern)
- `practices/no-debug-leftovers`: No debugging output left in shipped code: dbg!(), console.log(), console.debug() — why: Debug prints leak data into logs and bury real messages; use the project's logger with a level (check: code-pattern)
- `practices/no-secret-shapes`: No secret in source: no AWS key id, private key block, or a password, token or API key written as a literal — why: Agents paste credentials to make a call work, and git keeps them forever. Read secrets from the environment or a secret store; rotate any key that was committed (check: code-pattern)
- `practices/design-tokens-not-raw-colors`: Interface code uses the design tokens, not raw colors: no #rrggbb, #rgb or rgb()/rgba() literal outside the token file — why: A raw color is a fork of the theme: dark mode, contrast and rebranding miss it. Scope this rule to the UI folders and keep the tokens in one file it does not cover (check: code-pattern)
- `practices/no-raw-pixel-sizes`: Interface code uses the spacing and size scale, not raw pixel literals like '13px' — why: Raw sizes drift one screen at a time; a scale keeps rhythm and density consistent. Scope this rule to the UI folders (check: code-pattern)
- `practices/no-copied-files`: A variant lives in the original component, not in a copy: no Calendar2, auth_new, view_old, x_copy or x_backup files — why: A copied file forks the logic: fixes land in one copy only. Extend the original with a variant or a parameter (and record the variant in the manifest) (check: pattern)

### Commands

- `harna validate --changed` — the burst keeps the manifest, rules and parity [local]
- `cargo fmt --all --check` — rustfmt-clean (the craft gate) [both]
- `cargo clippy --workspace --all-targets -- -D warnings` — no clippy warnings (the craft gate) [both]
- `harna migrate --check` — every .harna/ file is current and reads with this harna (the format promise) [both]
- `harna preflight` — validation, doctor, parity, map current — releasable [both]
- `cargo test --workspace` — every unit, integration and scenario test [both]
